## 2. 订单状态机

### 2.1 三维状态模型

| 字段 | 类型 | 值域 | 维度说明 | 写入者 |
|---|---|---|---|---|
| `status` | char(1) | '0'~'5' | 主生命周期 | 订单引擎 |
| `pay_status` | char(1) | '0'未支付 '1'已支付 '2'已退款 | 支付维度 | 支付回调 |
| `delivery_status` | char(1) | '0'未配送 '1'配送中 '2'已送达 '3'已确认 | 物流维度 | 供货商+配送员 |
| `version` | int | 0~N | 乐观锁 | 订单引擎 |

三个字段**正交**，互不耦合：

```
一个订单的典型生命周期（三维联动）：
            status     pay_status  delivery_status
下单        0           0           0
支付回调    1           1           0
供货商发货  2           1           1
配送员送达  2           1           2
确认收货    3           1           3
取消订单    4           (不变)       (不变)
申请售后    5           (不变)       (不变)
```

### 2.2 status 主状态

| 值 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| '0' | 待支付 | 下单成功（已预占库存） | 支付成功 / 超时取消 / 用户取消 |
| '1' | 待发货 | 支付回调成功 | 供货商发货 |
| '2' | 配送中 | 供货商点击发货 | 客户确认收货 / 超时自动确认 |
| '3' | 已完成 | 客户确认或超时确认 | —（终态，不可再修改） |
| '4' | 已取消 | 取消操作（已释放库存+优惠券） | —（终态） |
| '5' | 售后中 | 客户申请售后 | 退款完成 / 售后关闭 |

## 3. 核心并发问题分析

### 3.1 竞态场景清单

```
┌────────────────────────────────────────────────────────┐
│ 场景 A：两个用户抢最后一个库存                          │
│ 线程1: 查库存 = 1                                      │
│ 线程2: 查库存 = 1  ← 脏读                              │
│ 结果：两人都下单成功 → 超卖                            │
├────────────────────────────────────────────────────────┤
│ 场景 B：支付回调 vs 用户取消 同时                      │
│ 线程1(支付): status='0' → 改 '1'                      │
│ 线程2(取消): status='0' → 改 '4'  ← 覆盖了支付结果    │
│ 结果：支付成功但订单显示已取消                         │
├────────────────────────────────────────────────────────┤
│ 场景 C：配送员 A 和 B 同时抢同一单                     │
│ 线程A: delivery_by=NULL → set delivery_by=A           │
│ 线程B: delivery_by=NULL → set delivery_by=B  ← 覆盖    │
│ 结果：一个订单被两个配送员接单                         │
├────────────────────────────────────────────────────────┤
│ 场景 D：微信重复回调（网络抖动，回调 2 次）            │
│ 线程1: pay_status='0' → 改 '1', 送优惠券              │
│ 线程2: pay_status='0' → 改 '1', 送优惠券  ← 重复送   │
│ 结果：用户收到双倍优惠                                 │
├────────────────────────────────────────────────────────┤
│ 场景 E：取消订单时 MQ 消息丢失                         │
│ 事务提交: status='4', 归还库存                         │
│ MQ消息: "支付成功，请改状态" (消息先到了)              │
│ 结果：取消后又变回待发货，库存也归还了                 │
└────────────────────────────────────────────────────────┘
```

### 3.2 解决方案矩阵

| 场景 | 问题 | 方案 | 机制 |
|---|---|---|---|
| A | 超卖 | **乐观锁扣库存** | SQL `WHERE stock >= qty AND version = ?` |
| B | 状态覆盖 | **乐观锁 + 合法性校验** | `WHERE version = ?` + 校验前置条件 |
| C | 重复接单 | **订单维度分布式锁** | `RedissonClient.getLock("delivery:order:" + orderId)` |
| D | 回调重复 | **幂等表 + 唯一索引** | `transaction_id` UNIQUE，`pay_status='1'` 时直接 return |
| E | 消息乱序 | **状态机校验 + 最终一致性** | 消费者校验当前 status 是否合法 target |

## 4. 各操作的事务边界与锁设计

### 4.1 创建订单（防超卖核心）

```
请求路径：POST /api/v1/order/create
并发风险：★★★★★（核心入口）

事务边界：
┌────────────────────────────────────────────────┐
│  ① 生成 order_no（雪花算法）                     │
│  ② 扣库存（乐观锁）                              │
│     UPDATE product_sku                           │
│     SET stock = stock - #{qty}, version = v+1    │
│     WHERE id = ? AND stock >= #{qty}              │
│     AND version = #{oldVersion}                  │
│     ↑ 返回受影响行数 = 0 → 库存不足，抛异常回滚   │
│  ③ INSERT order_info (status='0')                │
│  ④ INSERT order_bill（费用明细）                   │
│  ⑤ INSERT order_item（商品明细）                   │
│  ⑥ INSERT order_log（操作流水）                    │
│  ⑦ 发 MQ 延迟消息（30min 超时取消）                │
└────────────────────────────────────────────────┘
         │
         ├── 全部成功 → COMMIT，返回 order_no
         └── 任何一步失败 → ROLLBACK，库存归零
```

**关键细节：**

```java
@Override
@Transactional(rollbackFor = Exception.class)
public String createOrder(CreateOrderRequest request) {
    // ① 幂等：order_no 唯一索引，相同流水报错
    String orderNo = IdUtils.fastSimpleUUID();

    // ② 乐观锁扣库存（多个商品在 for 循环内依次扣）
    for (SkuItem item : request.getSkuList()) {
        int rows = productSkuMapper.deductStock(item.getSkuId(), item.getQuantity());
        if (rows == 0) {
            throw new ServiceException("商品库存不足: skuId=" + item.getSkuId());
        }
    }

    // ③ 写订单
    orderInfo.setOrderNo(orderNo);
    orderInfo.setStatus("0");
    orderInfo.setVersion(0);
    baseMapper.insert(orderInfo);

    // ④ 写流水日志
    orderLogMapper.insert(new OrderLog(orderId, orderNo, "0", null, "0", "用户" + userId, "下单"));

    // ⑤ MQ：延迟 30 分钟检查超时
    rocketMqProducer.sendDelay("order-timeout-cancel", orderNo, 30 * 60);

    return orderNo;
}
```

**关于 `@Transactional` 的正确使用：**

```java
// ❌ 错误：事务内调远程 RPC（连接池撑爆）
@Transactional
public void createOrder() {
    deductStock();              // 本地事务
    String result = remoteService.callRpc();  // 远程调用，可能等 5 秒
    insertOrder();              // 事务一直被远程调用阻塞
}

// ✅ 正确：RPC 放在事务外
public void createOrder() {
    // 1. 先做远程调用
    String result = remoteService.callRpc();

    // 2. 再在事务内处理数据
    doCreateOrderInTransaction(result);
}

@Transactional(rollbackFor = Exception.class)
public void doCreateOrderInTransaction(String result) {
    deductStock();
    insertOrder();
}
```

### 4.2 支付回调（防重复 + 乱序）

```
入口：微信服务器 → POST /api/v1/payment/callback
并发风险：★★★★（微信最多回调 5 次，可能重叠）

防线一：幂等表
  transaction_id 设为 UNIQUE KEY
  INSERT INTO payment_info (transaction_id, ...) 时，
  重复的 transaction_id 会抛 DuplicateKeyException → 直接 return

防线二：状态校验
  order_info.pay_status = '1' 说明已完成 → 直接 return

防线三：乐观锁
  UPDATE order_info SET status='1', pay_status='1', version=v+1
  WHERE order_no=? AND status='0' AND version=?

完整代码：
```

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void handlePayCallback(PayCallbackRequest request) {
    // 防线 1：幂等表唯一索引
    try {
        paymentInfoMapper.insert(PaymentInfo.builder()
            .transactionId(request.getTransactionId())
            .orderNo(request.getOrderNo())
            .paymentStatus(1)
            .build());
    } catch (DuplicateKeyException e) {
        log.warn("重复回调，已处理：{}", request.getTransactionId());
        return;
    }

    // 防线 2：状态校验（兜底）
    OrderInfo order = orderInfoMapper.selectByOrderNo(request.getOrderNo());
    if ("1".equals(order.getPayStatus())) {
        return;
    }

    // 防线 3：乐观锁更新
    int rows = orderInfoMapper.updateStatusByVersion(
        request.getOrderNo(), "1", "0", order.getVersion()
    );
    if (rows == 0) {
        throw new ServiceException("订单状态异常，可能已被取消，orderNo=" + request.getOrderNo());
    }

    // 写流水
    orderLogMapper.insert(new OrderLog(order.getId(), request.getOrderNo(),
        "1", "0", "1", "系统", "微信支付回调成功"));
}
```

### 4.3 取消订单（状态校验 + 资源回滚）

```
入口：POST /api/v1/order/cancel
风险：支付回调 与 取消 并发 → 乐观锁保证只有一个生效

事务边界：
┌────────────────────────────────────────────────┐
│  ① 校验 status 可取消（仅 '0' 可取消）          │
│  ② 乐观锁更新 status='4', version=v+1           │
│     WHERE order_no=? AND status='0' AND version=?│
│     ↑ 返回 0 → 已经被支付或已取消，抛异常        │
│  ③ 归还库存（回滚扣减）                          │
│  ④ 归还优惠券（coupon_user.status='0'）         │
│  ⑤ 写流水                                        │
└────────────────────────────────────────────────┘

PS：'1'（待发货）需要客服取消，因涉及退款流程
```

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void cancelOrder(String orderNo, String closeType, String reason) {
    OrderInfo order = orderInfoMapper.selectByOrderNo(orderNo);

    // 状态校验：仅待支付可自助取消
    if (!"0".equals(order.getStatus())) {
        throw new ServiceException("当前订单状态不允许取消");
    }

    // 乐观锁更新
    int rows = orderInfoMapper.cancelOrder(orderNo, order.getVersion(),
        closeType, reason);
    if (rows == 0) {
        throw new ServiceException("订单已被其他操作修改，请重试");
    }

    // 归还库存（根据 order_item 回滚）
    List<OrderItem> items = orderItemMapper.selectByOrderId(order.getId());
    for (OrderItem item : items) {
        productSkuMapper.restoreStock(item.getSkuId(), item.getQuantity());
    }

    // 归还优惠券
    if (StringUtils.isNotBlank(order.getCouponIds())) {
        couponUserMapper.releaseCoupon(order.getCouponIds(), order.getUserId());
    }

    // 写流水
    orderLogMapper.insert(/* ... */);

    // 如果已支付，需发起退款
    if ("1".equals(order.getPayStatus())) {
        paymentService.refund(orderNo);
    }
}
```

### 4.5 配送员接单（分布式锁防重复接单）

配送员接单不同于普通状态变更——**同一个订单不能被两个配送员同时接**。乐观锁不够，因为两次 UPDATE 分别在不同事务里，中间有间隙。

要用**分布式锁**：

```java
@Override
public void acceptDelivery(String orderNo, Long deliveryUserId) {
    // 订单粒度分布式锁
    RLock lock = redissonClient.getLock("delivery:accept:" + orderNo);
    try {
        // 尝试加锁，最多等 3 秒，锁自动续期（看门狗）
        if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
            throw new ServiceException("系统繁忙，请稍后重试");
        }

        // 锁内查询+校验
        OrderInfo order = orderInfoMapper.selectByOrderNo(orderNo);
        if (order.getDeliveryBy() != null) {
            throw new ServiceException("该订单已被其他配送员接单");
        }
        if (!"2".equals(order.getStatus())) {
            throw new ServiceException("订单状态异常，无法接单");
        }

        // 更新
        doAcceptInTransaction(orderNo, deliveryUserId);

    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new ServiceException("系统繁忙");
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}

@Transactional(rollbackFor = Exception.class)
public void doAcceptInTransaction(String orderNo, Long deliveryUserId) {
    int rows = orderInfoMapper.assignDelivery(orderNo, deliveryUserId);
    if (rows == 0) {
        throw new ServiceException("已被其他配送员接单");
    }
    orderLogMapper.insert(/* ... */);
}
```

```sql
-- Mapper.xml
<update id="assignDelivery">
    UPDATE order_info
    SET delivery_by = #{deliveryUserId},
        delivery_status = '1',
        update_time = NOW()
    WHERE order_no = #{orderNo}
      AND delivery_by IS NULL        -- 关键：没被接走过才更新
</update>
```

> **为什么配送员接单要用分布式锁，而其他操作只用乐观锁？**
> 乐观锁的语义是「谁先提交谁赢」，适合短事务自动重试。但配送员接单涉及：查订单 → 看地址 → 判断接不接，这个过程用户需要几秒钟思考。分布式锁在这几秒内挡住其他人，避免用户点进去发现被抢了。

### 5.1 幂等入口清单

```
┌────────────────────────────────────────────────────────────────┐
│ 入口                       风险原因        幂等方案             │
├────────────────────────────────────────────────────────────────┤

│ ④ 配送员送达确认           网络抖动        请求方携带幂等 token  │
│ ⑤ 用户确认收货             重复点击        接口幂等+乐观锁      │
│ ⑥ 退款回调                 同支付回调      同 ②                │
└────────────────────────────────────────────────────────────────┘
```

### 5.2 去重表模式（通用幂等方案）

```sql
-- 去重表（所有可能重复的入口共用）
CREATE TABLE idempotent_record (
    idempotent_key   varchar(64) PRIMARY KEY COMMENT '幂等 key：业务前缀+业务ID',
    status           char(1)     DEFAULT '0' COMMENT '0-处理中 1-已完成',
    create_time      datetime    DEFAULT CURRENT_TIMESTAMP,
    finish_time      datetime    COMMENT '完成时间',
    response_body    text        COMMENT '上一次的返回结果（同一结果返回）',
    UNIQUE KEY uk_key (idempotent_key)
) ENGINE=InnoDB COMMENT='幂等去重表';

-- 使用方式（每个入口统一加）：
-- ① INSERT INTO idempotent_record (idempotent_key) VALUES (?)
--    成功 → 继续处理
--    失败（DuplicateKey）→ 已有记录，查 status：
--      如果 ='1' → 直接返回上次 response_body
--      如果 ='0' → 等待或报"正在处理"
-- ② 业务完成后 UPDATE status='1', response_body=?
```

## 6. 线程池隔离与异步

### 6.1 线程池规划

系统中有三个异步场景，**必须用不同的线程池隔离**，防止相互干扰：

```
业务              线程池名称      核心线程  队列   拒绝策略
────────────────────────────────────────────────────────
支付回调处理      pay-callback     4       100    CallerRuns
订单超时取消      order-timeout    2       50     Discard
售后处理          after-sale        2       50     CallerRuns
```

```java
@Configuration
public class ThreadPoolConfig {

    @Bean("payCallbackExecutor")
    public ThreadPoolTaskExecutor payCallbackExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("pay-cb-");
        // 关键：拒绝策略用 CallerRuns——压到调用方线程慢慢处理，比丢消息强
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }

    @Bean("orderTimeoutExecutor")
    public ThreadPoolTaskExecutor orderTimeoutExecutor() {
        // 超时取消允许丢（DiscardPolicy）
        // 大不了用户重新取消，不影响核心业务
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(2);
        executor.setMaxPoolSize(4);
        executor.setQueueCapacity(50);
        executor.setThreadNamePrefix("timeout-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.DiscardPolicy());
        executor.initialize();
        return executor;
    }
}
```

## 7. 超时机制与补偿

### 7.1 超时场景

```
场景                  延迟       消费者做什么         失败补偿
─────────────────────────────────────────────────────────────
待支付取消            30min      检查 status='0'      → 取消，归库存+券
送达后自动确认         7天        检查 delivery=2       → 完成
售后超时自动同意       7天        （暂不实现）          手动处理
```

### 7.2 补偿对账定时任务

每天凌晨跑一次，解决「消息丢了」或「回调没到」的问题。

```java
@Component
public class OrderReconcileTask {

    /**
     * 每天凌晨 2:00 执行
     * 0 0 2 * * ?
     */
    @Scheduled(cron = "0 0 2 * * ?")
    public void reconcile() {
        // ① 找「已支付但订单状态没变」的单子
        List<PaymentInfo> abnormal = paymentInfoMapper.selectAbnormalPayments();
        for (PaymentInfo pay : abnormal) {
            // 微信确认已支付 → 补改订单状态
            orderService.handlePayCallback(pay);
        }

        // ② 找「已超时但没取消」的单子
        List<OrderInfo> timeoutOrders = orderInfoMapper.selectTimeoutOrders();
        for (OrderInfo order : timeoutOrders) {
            orderService.cancelOrder(order.getOrderNo(), "2", "超时未支付（对账补偿）");
        }

        // ③ 找「配送员已送达7天未确认」的单子
        List<OrderInfo> unconfirmed = orderInfoMapper.selectDeliveryTimeoutOrders();
        for (OrderInfo order : unconfirmed) {
            orderService.autoConfirm(order.getOrderNo());
        }
    }
}
```

```sql
  AND status   = #{expectedStatus}    -- 前置状态校验
```

### 8.2 扣库存（防超卖核心）

```sql
<update id="deductStock">
    UPDATE product_sku
    SET stock   = stock - #{quantity},
        version = version + 1
    WHERE id       = #{skuId}
      AND stock   >= #{quantity}     -- 防超卖：库存不够就不减
      AND version  = #{oldVersion}
</update>
```

```sql
<update id="restoreStock">
    UPDATE product_sku
    SET stock   = stock + #{quantity},
        version = version + 1
    WHERE id      = #{skuId}
      AND version = #{oldVersion}
</update>
```

## 12. 层级调用约束

```
Controller（薄到不能再薄）
  │ 参数校验 (@Valid + @NotBlank)
  │ 调用 Service
  │ 返回 R<T>
  │
Service 接口
  │ 定义方法签名
  │
ServiceImpl（全部业务逻辑在这里）
  │ @Transactional(rollbackFor = Exception.class)
  │ 事务：只包含 Mapper 操作，不包含远程调用
  │ 锁：在 Service 层方法内加锁，事务外获取锁
  │
Mapper + XML
    SQL 层只写数据，不写逻辑
```

```
锁与事务的执行顺序（必须遵守）：
  ❌ 错误：
    @Transactional
    void method() {
        lock.lock();      // 锁在事务内
        // ... 此时事务没提交，锁没释放，其他线程在等锁
        // 锁提交后，锁释放，其他线程看到旧数据
    }

  ✅ 正确：
    void method() {
        lock.lock();      // 锁在事务外获取
        try {
            doInTx();     // 事务内处理
        } finally {
            lock.unlock(); // 事务提交后释放锁
        }
    }

    @Transactional
    void doInTx() { ... }
```
