# Feature Specification: 商家端 Web 后台

**Feature Branch**: `005-merchant-web-portal`

**Created**: 2026-06-25

**Status**: Draft

**Input**: 完成商家功能，目前让商家使用web端，使用高级编程，不写低质量代码

## User Scenarios & Testing

### User Story 1 — 商家登录与权限隔离 (Priority: P1)

商家通过独立登录入口进入商家后台，看到的只是自己店铺的数据。登录校验店铺状态（已审核通过才可登录），未审核/已关闭的店铺无法登录。

**Why this priority**: 没有登录认证和权限隔离，其他功能无从谈起。商家必须能安全地访问自己的数据，不能看到其他商家的信息。

**Independent Test**: 商家 A 登录 → 看到自己店铺的商品和订单 → 无法看到商家 B 的数据。未审核商家尝试登录 → 提示"店铺未审核通过"。

**Acceptance Scenarios**:

1. **Given** 管理员已审核通过商家 A 的店铺，**When** 商家 A 使用账号密码登录商家后台，**Then** 系统验证凭据并返回商家角色 token，跳转至商家控制台首页
2. **Given** 商家 A 已登录，**When** 商家 A 浏览商品管理页面，**Then** 仅展示商家 A 自己的商品，不包含其他商家的数据
3. **Given** 商家的店铺状态为"待审核"或"已关闭"，**When** 商家尝试登录，**Then** 登录失败并提示"店铺未审核通过"
4. **Given** 管理员账号登录，**When** 管理员访问商家后台的订单管理，**Then** 展示所有商家的订单（管理端权限）

---

### User Story 2 — 商家管理店铺商品 (Priority: P1)

商家在后台管理自己店铺的商品：新增/编辑/上下架商品、管理 SKU、查看商品列表。

**Why this priority**: 商品是电商的核心，商家必须先能管理自己的商品才能接单。

**Independent Test**: 商家登录 → 商品管理 → 新增商品 → 上架 → 在商品列表看到自己的商品。

**Acceptance Scenarios**:

1. **Given** 商家 A 已登录，**When** 商家在商品管理页面点击"新增商品"，**Then** 填写商品信息（名称/描述/分类/图片/价格/SKU）→ 提交后该商品关联商家 A 的店铺，商品状态为"下架"
2. **Given** 商家新增商品完成，**When** 商家点击"上架"，**Then** 商品状态变为"上架"，在前端可见
3. **Given** 商品已上架，**When** 商家点击"下架"，**Then** 商品在前端不可见，但数据保留
4. **Given** 商家 A 查看商品列表，**When** 进入商品管理页面，**Then** 仅显示商家 A 自己的商品，支持按名称/状态筛选
5. **Given** 商家 A 新增商品时选择了分类，**When** 查看分类树，**Then** 展示所有可用的分类（分类由管理员统一管理）

---

### User Story 3 — 订单管理 (Priority: P1)

商家查看自己店铺的订单列表和详情，进行发货操作（录入配送员信息）。

**Why this priority**: 商家需要知道谁买了什么，并在发货后更新订单状态。发货是订单流程的关键节点。

**Independent Test**: 商家登录 → 订单管理 → 查看待发货订单 → 点击发货 → 输入配送员信息 → 订单变为配送中。

**Acceptance Scenarios**:

1. **Given** 有用户下单购买了商家 A 的商品，**When** 商家 A 查看订单列表，**Then** 看到该订单，订单状态为"待发货"（附带收货地址、商品明细、实付金额）
2. **Given** 商家 A 选择待发货订单点击"发货"，**When** 商家录入配送员姓名和电话，**Then** 订单状态变为"配送中"，配送员信息记录到订单
3. **Given** 订单已完成（用户确认收货），**When** 商家查看订单详情，**Then** 看到订单为"已完成"状态
4. **Given** 商家 A 查看订单列表，**When** 按状态筛选（待发货/配送中/已完成/已取消），**Then** 正确筛选出对应状态的订单

---

### User Story 4 — 售后审核 (Priority: P2)

商家查看用户提交的售后申请，审核同意或拒绝退款。

**Why this priority**: 售后涉及资金安全，但频率低于日常订单处理和商品管理。

**Independent Test**: 商家登录 → 售后管理 → 看到售后申请 → 同意退款 → 系统自动退款 → 订单状态变为已取消。

**Acceptance Scenarios**:

1. **Given** 用户对商家 A 的订单提交了售后申请，**When** 商家 A 查看售后列表，**Then** 看到该申请，显示退款原因、退款金额、订单号
2. **Given** 商家 A 点击"同意退款"，**When** 系统处理退款，**Then** 退款原路返回，订单状态变为已取消，用户收到通知
3. **Given** 商家 A 点击"拒绝退款"，**When** 提交拒绝理由，**Then** 售后申请流转到客服/管理员处理，用户可看到商家拒绝的理由
4. **Given** 商家同意或拒绝后，**When** 查看售后列表，**Then** 该申请的状态已更新

---

### User Story 5 — 店铺信息与数据概览 (Priority: P3)

商家查看和编辑自己店铺的基本信息，查看简单的营业数据。

**Why this priority**: 数据概览提供经营参考，但非核心功能。

**Independent Test**: 商家登录 → 店铺设置 → 修改店铺名称/简介 → 保存成功。商家登录首页 → 看到今日订单数和销售额。

**Acceptance Scenarios**:

1. **Given** 商家 A 登录后台首页，**When** 进入控制台首页，**Then** 看到今日订单数量、今日销售额、待处理订单数
2. **Given** 商家 A 进入"店铺设置"页面，**When** 修改店铺名称、简介、联系电话等信息并保存，**Then** 信息更新成功
3. **Given** 商家 A 修改了店铺信息，**When** 管理员在商家管理页面查看，**Then** 看到更新后的信息

---

### Edge Cases

- **多商家共享分类体系**：分类由管理员统一管理，商家只能选择已有分类，不能新建分类
- **商品删除安全**：已有订单的商品不能被删除，只可下架
- **订单数据权限**：商家只能看自己店铺的订单，不能看到其他店铺的订单数据
- **商家并发发货**：同一订单不能被两个商家重复发货
- **售后超时处理**：商家 48 小时未处理售后申请，系统自动流转到客服/管理员处理
- **配送员录入**：商家手动录入配送员姓名+电话，没有独立的配送员账号系统
- **商品 SKU 管理**：一个商品可包含多个 SKU（规格），商家需能为商品添加/编辑/删除 SKU

## Requirements

### Functional Requirements

**商家登录与权限**

- **FR-001**: 商家 MUST 使用独立的登录入口进入商家后台，登录凭据与管理员系统隔离
- **FR-002**: 系统 MUST 在商家登录时校验店铺状态，仅"已启用"状态的店铺允许登录
- **FR-003**: 商家 MUST 只能操作和查看自己店铺的数据（商品/订单/售后），不能跨店铺操作
- **FR-004**: 管理员 MUST 能查看和管理所有商家的数据（保留现有权限）

**商品管理**

- **FR-005**: 商家 MUST 能查看自己店铺的商品列表，支持按名称/状态搜索
- **FR-006**: 商家 MUST 能新增商品，包括填写商品名称、描述、分类、图片、价格、排序等信息
- **FR-007**: 商家 MUST 能为商品管理 SKU（新增/编辑/删除），SKU 包含规格名称、价格、库存
- **FR-008**: 商家 MUST 能上架/下架商品，下架商品在前端不可见
- **FR-009**: 商家 MUST 能编辑商品基本信息（名称、描述、图片、价格等）
- **FR-010**: 分类由管理员统一维护，商家只能选择已有分类，不能创建/修改分类

**订单管理**

- **FR-011**: 商家 MUST 能查看自己店铺的订单列表，支持按状态/时间筛选
- **FR-012**: 商家 MUST 能查看订单详情（商品明细、收货地址、实付金额、支付方式等）
- **FR-013**: 商家 MUST 能对待发货订单进行发货操作，录入配送员姓名和联系电话
- **FR-014**: 系统 MUST 在商家发货后更新订单状态为"配送中"，并记录配送员信息

**售后管理**

- **FR-015**: 商家 MUST 能查看用户提交的售后申请列表
- **FR-016**: 商家 MUST 能审核售后申请（同意/拒绝），拒绝时需填写拒绝理由
- **FR-017**: 商家同意退款后，系统 MUST 自动执行退款流程（调用支付侧退款接口）
- **FR-018**: 商家拒绝退款后，售后申请 MUST 自动流转到客服/管理员处理
- **FR-019**: 商家拒绝后即转客服处理，商家不可再操作此申请。客服/管理员做最终决定。

**店铺设置**

- **FR-020**: 商家 MUST 能编辑自己店铺的基本信息（店铺名称、简介、联系电话、店铺地址、店铺 logo）
- **FR-021**: 商家 MUST 能修改登录密码

**数据概览**

- **FR-022**: 商家登录后 MUST 看到今日订单数、今日销售额、待处理订单数、待发货订单数

### Key Entities

- **商家 (MerchantInfo)** : 店铺基本信息，关联用户ID（新建）。已有 merchant_info 表（name/contactName/contactPhone/address/logo/description/status/auditRemark/auditTime），需增加 user_id 字段关联商家登录账号
- **商品 (Product)** : 需增加 merchant_id 字段标识所属商家。已有 Product entity（share-goods）
- **SKU (ProductSku)** : 商品规格，关联商品。已有 ProductSku entity（share-goods）
- **分类 (Category)** : 商品分类，由管理员统一管理。已有 Category entity（share-goods）
- **订单 (OrderInfo)** : 已有订单实体，包含 merchant_id 字段。需确认查询时按 merchant_id 过滤
- **售后申请 (AfterSaleRequest)** : 已有 after_sale_request 表，包含 merchant_id 字段
- **配送信息** : order_info 已有 delivery_by/delivery_name/delivery_phone 字段

## Success Criteria

### Measurable Outcomes

- **SC-001**: 商家从登录到看到控制台首页 < 3 秒（含鉴权校验）
- **SC-002**: 商家新增一个商品（含 3 个 SKU）完成 < 2 分钟
- **SC-003**: 商家完成发货操作（找到订单 → 填写配送员 → 确认）< 30 秒
- **SC-004**: 商家审核售后（查看申请 → 同意/拒绝）< 15 秒
- **SC-005**: 商家 A 在任何页面上都看不到商家 B 的任何数据（数据隔离 100%）
- **SC-006**: 未审核店铺无法登录商家后台（权限拦截 100%）
- **SC-007**: 商品上架/下架后，前端在 5 秒内反映状态变更

## Assumptions

- **复用现有 RuoYi 前端框架**：商家后台基于 share-ui（Vue 3 + Element Plus）扩展，新增商家角色路由，不新建前端工程
- **复用现有 share-auth 认证体系**：扩展认证中心支持商家角色登录，商家账号在 share-system 或新建 merchant_user 表中管理，登录后下发商家角色 token
- **商品表增加商户关联**：Product entity 增加 merchant_id 字段，与商家绑定。此变更需数据库迁移
- **订单已有 merchant_id**：order_info 表已有 merchant_id（假设），查询时过滤
- **配送员无独立模块**：发货时商家手动录入配送员姓名+电话，不建立配送员账号体系
- **商家只能使用 Web 后台**：不包含商家小程序
- **管理端保留现有所有功能**：管理员仍然可以管理所有商家的商品/订单/售后
- **数据库迁移**：product 表需新增 merchant_id 字段，merchant_info 表需新增 user_id 字段
- **前端构建部署流程不变**：Vue 3 + Vite + Element Plus 构建，部署到 VM nginx
