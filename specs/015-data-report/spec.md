# Feature Specification: 平台数据报表

**Feature Branch**: `015-data-report`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: "数据报表 开发这个接口，自己判断属于哪个角色、缺不缺表/字段。请贴合此项目并摸清此接口痛点，最后解决。"

## User Scenarios & Testing

### User Story 1 - 交易总览（平台管理员首页概览） (Priority: P1)

作为平台管理员，我想在后台首页看到平台的交易核心指标（今日/本周/本月订单数、交易额、客单价），以便快速掌握平台经营状况。

**Why this priority**: 这是管理员最常查看的数据，是数据报表的核心入口，提供即时经营概览。

**Independent Test**: 登录管理后台 → 访问数据概览页面 → 查看今日/本周/本月订单数、交易额、客单价、退款金额等指标，数据与实际订单数据一致。

**Acceptance Scenarios**:

1. **Given** 平台有已完成订单存在, **When** 管理员访问交易总览, **Then** 返回今日订单数、今日交易额、今日客单价
2. **Given** 当日无订单, **When** 管理员访问交易总览, **Then** 今日指标返回 0
3. **Given** 管理员指定日期范围, **When** 查询交易总览, **Then** 返回该范围内的订单数、交易额、退款金额

---

### User Story 2 - 订单趋势（折线图数据） (Priority: P1)

作为平台管理员，我想查看指定时间段内的每日订单数和交易额趋势，以便分析平台业务的增长趋势和波动。

**Why this priority**: 趋势分析是经营决策的基础，帮助管理员发现业务增长或下降的信号。

**Independent Test**: 选择日期范围 → 获取每日订单数和交易额列表 → 返回数据按日期排序，适用于绘制折线图。

**Acceptance Scenarios**:

1. **Given** 管理员选择近7天, **When** 查询订单趋势, **Then** 返回最近7天每天的订单数和交易额
2. **Given** 某天无订单, **When** 查询订单趋势, **Then** 该日返回订单数0、交易额0
3. **Given** 管理员选择跨月日期范围, **When** 查询订单趋势, **Then** 按天返回整个范围内的数据

---

### User Story 3 - 商品销售排行 (Priority: P2)

作为平台管理员，我想查看商品销售排行（按销量或交易额降序），以便了解哪些商品最受欢迎、哪些贡献了主要收入。

**Why this priority**: 商品排行帮助管理员识别爆款和滞销品，指导选品和营销策略。

**Independent Test**: 访问商品排行页面 → 选择排序方式（销量/交易额）→ 返回 Top N 商品列表含商品名、销量、交易额。

**Acceptance Scenarios**:

1. **Given** 存在多个商品有销售记录, **When** 查询商品销售排行（按销量降序）, **Then** 返回按销量排序的商品列表
2. **Given** 存在多个商品有销售记录, **When** 查询商品销售排行（按交易额降序）, **Then** 返回按交易额排序的商品列表
3. **Given** 指定日期范围, **When** 查询商品销售排行, **Then** 仅统计该范围内的销售数据
4. **Given** 某商品有退款记录, **When** 查询商品销售排行, **Then** 交易额应扣除退款金额

---

### User Story 4 - 商家销售排行 (Priority: P2)

作为平台管理员，我想查看商家销售排行，以便了解各商家的经营表现，对业绩不佳的商家进行帮扶或调整。

**Why this priority**: 平台需要了解入驻商家的贡献度分布，为运营决策提供数据支撑。

**Independent Test**: 访问商家排行页面 → 返回按交易额降序的商家列表含商家名、订单数、交易额。

**Acceptance Scenarios**:

1. **Given** 多个商家有销售记录, **When** 查询商家销售排行, **Then** 返回按交易额排序的商家列表
2. **Given** 指定日期范围, **When** 查询商家销售排行, **Then** 仅统计该范围内的数据
3. **Given** 某商家无订单, **When** 查询商家销售排行, **Then** 该商家仍出现在列表中，数据为 0

---

### User Story 5 - 用户统计 (Priority: P3)

作为平台管理员，我想查看用户相关统计数据（总用户数、新增用户数、活跃用户数），以便了解平台的用户增长和活跃情况。

**Why this priority**: 用户增长是平台健康度的重要指标，对评估拉新效果和用户留存有参考价值。

**Independent Test**: 访问用户统计页面 → 查看总用户数、今日/本周/本月新增用户数。

**Acceptance Scenarios**:

1. **Given** 平台有注册用户, **When** 查询用户统计, **Then** 返回用户总数、今日新增数
2. **Given** 当日无新用户注册, **When** 查询用户统计, **Then** 今日新增数返回 0
3. **Given** 管理员指定日期范围, **When** 查询新增用户趋势, **Then** 返回每日新增用户数列表

---

### User Story 6 - 支付统计 (Priority: P3)

作为平台管理员，我想查看支付方式分布和支付金额统计，以便了解用户的支付偏好。

**Why this priority**: 支付数据有助于评估支付渠道的稳定性和用户偏好，为支付优化提供参考。

**Independent Test**: 访问支付统计页面 → 查看各支付方式的订单数和金额占比。

**Acceptance Scenarios**:

1. **Given** 存在多种支付方式的订单, **When** 查询支付统计, **Then** 返回各支付方式的订单数、金额及占比
2. **Given** 指定日期范围, **When** 查询支付统计, **Then** 仅统计该范围内的支付数据
3. **Given** 某支付方式在该范围内无订单, **When** 查询支付统计, **Then** 该支付方式的数据为 0

### Edge Cases

- 跨库查询时，如果 share_order/share_payment/share_user 等数据库连接超时或不可用，系统应返回友好提示而非直接报错
- 查询超大日期范围（如跨年）时，单次查询应在合理时间内返回（超时限制应合理设置）
- 全平台日订单量超过数万时，实时 COUNT/SUM 查询应仍能在秒级返回
- 商品销售排行中，已删除的商品应仍能显示商品名（从 order_item.product_name 取）
- 退款订单不应计入交易额统计，退款金额单独展示

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 提供交易总览接口，返回今日/本周/本月/指定时间范围的订单数、交易额、退款金额、客单价
- **FR-002**: 系统 MUST 提供订单趋势接口，返回指定日期范围内每天的订单数和交易额
- **FR-003**: 系统 MUST 提供商品销售排行接口，支持按销量或交易额排序，支持日期范围筛选
- **FR-004**: 系统 MUST 提供商家销售排行接口，按交易额排序，支持日期范围筛选
- **FR-005**: 系统 MUST 提供用户统计接口，返回总用户数、新增用户数（支持按日/周/月分组）
- **FR-006**: 系统 MUST 提供支付统计接口，返回各支付方式的订单数、金额及占比
- **FR-007**: 系统 MUST 支持所有统计接口按日期范围筛选（开始日期 ~ 结束日期）
- **FR-008**: 系统 MUST 对跨库查询的异常做降级处理（返回部分数据或友好错误提示）
- **FR-009**: 系统 SHOULD 在数据量较大时保证查询在可接受时间内完成（秒级响应）
- **FR-010**: 系统 MUST 拒绝未授权的访问（仅平台管理员角色可访问数据报表）

### Key Entities

- **OrderInfo (订单)**: 核心交易实体，含订单金额、支付状态、下单时间、支付时间，是交易统计的主要数据源
- **OrderItem (订单项)**: 订单中的商品明细，含商品ID、商品名、单价、数量，是商品排行的主要数据源
- **PaymentInfo (支付记录)**: 支付渠道记录，含支付方式、支付金额、支付状态，是支付统计的数据源
- **UserInfo (用户)**: 平台用户信息，含注册时间、最近登录时间、状态，是用户统计的数据源
- **MerchantInfo (商家)**: 商家信息，含入驻时间、状态，是商家排行统计的数据源

## Success Criteria

### Measurable Outcomes

- **SC-001**: 管理员可以在 3 步以内（打开页面 → 选择日期 → 查看数据）获取任意统计报表数据
- **SC-002**: 查询最近 30 天的趋势数据，响应时间不超过 3 秒（数据量在一万级订单以内）
- **SC-003**: 查询跨月/跨年的大范围统计数据，响应时间不超过 5 秒
- **SC-004**: 所有统计接口在数据库连接异常时，返回降级响应而非 500 错误
- **SC-005**: 管理员无需手动计算即可直接获取客单价、支付占比等衍生指标

## Assumptions

- 平台管理员指 share-system 模块的管理员用户，通过 `@RequiresPermissions` 鉴权
- 报表数据均从现有业务表实时聚合计算，无需预先建统计表或跑定时任务
- 跨库查询使用 MySQL 的 `db.table` 语法（已在 MerchantDashboard 中验证可行）
- 项目使用的 MySQL 版本（5.7.38）支持跨库查询
- 商品销量排行从 `share_order.order_item` 聚合计算，而非 `product.sales` 字段
- 数据报表模块部署在 share-system 服务中（平台管理后台标准模块）
- 退款统计从 `order_info.refund_amount` 字段获取，无需关联 payment_info
- 支付方式在 `payment_info.pay_way` 字段存储（0-微信支付，可能还有其它方式待确认）
