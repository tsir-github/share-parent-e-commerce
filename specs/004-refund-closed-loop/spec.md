## Clarifications

### Session 2026-06-24

- Q: US1 说"用户在小程序查看退款进度"，但 Assumptions 说当前 scope 不包含小程序前端，怎么处理？ → A: US1 只做管理端 + API，小程序前端另行开发

- Q: 售后类型是否需要区分"仅退款"与"退货退款"？ → A: 仅退款，本次不引入退货退款
- Q: 运费是否退？优惠券是否退回？商品需要退货吗？ → A: 全额退含运费和商品金额，优惠券不退（保留权益），商品不用退货。部分退款：按比例分摊退款额，运费和商品金额同比例退
- Q: 退款审核流程是什么？ → A: 商家先审核同意 → 系统自动退款；商家不同意 → 平台管理员/客服介入判定
- Q: 配送员和商家是什么关系？有没有已有的配送员模块？ → A: 目前商家和配送员视为一体，order_info 表已有 delivery_by/delivery_name/delivery_phone 字段，但不拆独立配送员模块

## User Scenarios & Testing

### User Story 1 — 管理员发起退款并同步订单状态 (Priority: P1)

商家/管理员在后台对已支付的订单发起退款（需商家先同意，不同意则客服介入）：退款金额通过原路退回（微信支付），全额退款 = 商品金额 + 运费，优惠券保留不退。商品无需退货。支付单状态更新为已退款，订单状态同步更新为已取消/已退款。

**Why this priority**: 退款涉及资金安全，订单状态和支付状态必须一致。当前支付侧退款已完成但订单侧未同步，属于数据一致性问题。

**Independent Test**: 管理员在后台选择已支付的订单 → 发起退款 → 确认退款金额 → 系统处理退款 → 查看订单状态变为已取消、支付状态变为已退款。

**Acceptance Scenarios**:

1. **Given** 存在已完成支付的订单，**When** 商家发起全额退款，**Then** 系统发起审核通知，等待商家确认（商家和管理员视为同一方，系统自动确认通过）
2. **Given** 商家同意全额退款，**When** 系统执行退款，**Then** 退还金额 = 商品金额 + 运费，优惠券保留不变，商品无需退货，调用微信退款接口，支付单状态变为退款中
3. **Given** 商家不同意退款，**When** 客服介入，**Then** 平台管理员可在后台强制发起退款或驳回
4. **Given** 微信退款成功异步通知到达，**When** 系统处理通知，**Then** 支付单状态更新为已退款，订单状态由售后中变为已取消，订单支付状态变为已退款
5. **Given** 订单已退款完成，**When** 用户查看订单详情，**Then** 看到订单状态为已取消（含退款完成标识），可查看退款金额和时间（当前 scope 仅提供 API 和数据结构，小程序端另行开发）
6. **Given** 退款金额超过订单实付金额，**When** 管理员发起退款，**Then** 系统拒绝并提示金额超限

---

### User Story 2 — 用户申请售后并查看进度 (Priority: P2)

用户在微信小程序中对已完成订单发起售后申请（仅退款模式，无实物回寄），填写原因和说明，提交后由管理员审核处理。用户可实时查看售后进度。

**Why this priority**: 用户自助售后是电商标准能力，减少客服人工处理成本。但涉及用户端小程序改动，优先级低于管理端。

**Independent Test**: 用户在订单详情页 → 申请售后 → 填写退款信息 → 提交 → 管理员在后台看到申请并处理 → 用户看到进度更新。

**Acceptance Scenarios**:

1. **Given** 用户已确认收货的订单，**When** 用户在订单详情页点击"申请售后"，**Then** 进入售后申请页面，可填写退款原因、补充说明（全额退款，商品无需退货）
2. **Given** 用户提交售后申请，**When** 商家在后台审核，**Then** 系统记录申请信息，订单状态变为售后中（status=5）
3. **Given** 商家同意退款，**When** 系统执行退款，**Then** 退还全额（商品金额+运费），优惠券保留，订单状态变为已取消
4. **Given** 商家不同意退款，**When** 平台管理员介入判定，**Then** 管理员可强制退款或驳回申请

---

### User Story 3 — 部分退款场景 (Priority: P3)

一张订单包含多个商品，部分商品退货退款，剩余商品保持原状态。仅退部分金额到用户账户。

**Why this priority**: 部分退款是完整售后能力的组成部分，但实现复杂（涉及按 SKU 分摊退款金额），优先级最低。

**Independent Test**: 管理员选择订单中的部分 SKU → 输入退款金额 → 确认 → 系统处理部分退款 → 订单主状态不变但退款相关字段更新。

**Acceptance Scenarios**:

1. **Given** 订单包含多个商品，**When** 管理员发起部分退款（仅退其中一件），**Then** 系统按指定金额退款，订单主状态保持不变，记录已退款金额和待退款金额
2. **Given** 部分退款完成后，**When** 后续对同一订单再次发起剩余商品退款，**Then** 系统正确处理，所有商品退完后订单状态变为已取消

---

### Edge Cases

- **退款驳回后订单状态恢复**：商家/管理员拒绝退款后，订单状态应从"售后中"恢复为原本状态（已完成）
- **商家不同意退款 → 客服介入**：商家拒绝退款后，平台管理员可在后台强制退款或驳回，管理员决定为最终决定
- **支付侧退款成功但 MQ 通知丢失**：补偿机制兜底，定时任务重发退款通知到订单侧
- **重复退款请求**：同一订单被多次发起退款，分布式锁 + 状态机校验防止重复退款
- **退款途中用户取消申请**：用户撤销售后申请后，订单状态恢复
- **微信退款失败处理**：微信返回退款失败（余额不足、账户异常等），系统记录失败原因并通知管理员人工处理
- **已取消订单不允许退款**：只有已支付/已完成状态的订单才能发起退款
- **商品无需退货**：社区电商模式，退款不涉及实物回寄

## Requirements

### Functional Requirements

- **FR-001**: 商家/管理员 MUST 能对已支付的订单发起退款（全款或部分）
- **FR-001a**: 用户 MUST 能对已完成订单申请售后（仅退款），由商家审核；商家不同意时平台客服介入
- **FR-002**: 全额退款金额 = 商品总金额（total_amount）+ 运费（freight_amount），优惠券不退（保留用户权益），商品无需退货
- **FR-003**: 退款审核流程：商家先审核同意 → 系统自动退款；商家不同意 → 平台管理员/客服介入判定，管理员决定为最终决定
- **FR-003a**: 商家审核超时未处理（如 48 小时），系统自动流转到平台管理员处理
- **FR-004**: 支付服务退款成功 MUST 通过消息队列通知订单服务更新订单状态
- **FR-005**: 订单服务 MUST 实现退款消息消费者，收到通知后将订单状态变更为已取消（如全额退款），支付状态变更为已退款
- **FR-006**: 所有退款消息消费者 MUST 幂等（状态机前置校验 + 唯一键去重），防止重复处理
- **FR-007**: 系统 MUST 提供定时任务补偿机制：扫描已退款但订单侧未同步的记录，重新发送通知
- **FR-008**: 订单状态变更为"售后中"时 MUST 记录操作日志（包含退款原因、退款金额、操作人）
- **FR-009**: C 端用户 MUST 能查看订单的退款进度和状态
- **FR-010**: 微信退款回调处理 MUST 幂等（已退款状态跳过）
- **FR-011**: 管理端退款操作 MUST 需权限校验
- **FR-012**: 部分退款场景下 MUST 记录已退款金额累计，不得超过订单可退总额
- **FR-013**: 系统 MUST 记录所有退款操作日志（操作时间、操作人、订单号、退款金额、变更前后状态），与订单操作日志体系一致

### Key Entities

- **支付记录 (payment_info)**: 记录支付订单的退款状态和退款金额。关联订单号。
- **订单主表 (order_info)**: 记录订单生命周期。已有 total_amount（商品总金额）、freight_amount（运费）、discount_amount（优惠金额）、pay_amount（实付金额）、coupon_ids（优惠券ID列表）、delivery_by/delivery_name/delivery_phone（配送员信息）等字段。增加退款相关状态字段（已退款金额、最近退款时间）。
- **订单操作日志 (order_log)**: 记录退款相关操作流水。当前已通过状态机自动记录。
- **退款消息 (MQ DTO)**: 退款通知传输对象，含订单号和交易流水号。参考现有 PaymentSuccessMessage 设计。
- **售后申请记录 (after_sale_request)**: 用户提交的售后申请（含退款原因、金额、状态、管理员处理意见）。US2 和 US3 需要。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 管理员发起退款到支付侧退款处理完成 < 5 秒
- **SC-002**: 退款成功后订单状态更新延迟 < 5 秒（MQ 通知 + 消费者处理）
- **SC-003**: 补偿机制无漏单：退款成功但未通知订单的记录在 2 分钟内被补偿处理
- **SC-004**: 重复退款请求不会导致同一订单被多次退款（幂等性 100%）
- **SC-005**: 所有退款操作 100% 可追溯审计，支持按订单号查询完整的退款操作时间线
- **SC-006**: 管理员可在 3 步内完成退款操作（搜索订单 → 查看详情 → 退款）
- **SC-007**: 用户申请售后到提交完成 < 2 分钟（US2）

## Assumptions

- **复用现有退款基础设施**：支付侧 refund() + handleRefundCallback 已实现，无需重写
- **复用现有消息队列模式**：沿用 RocketMQ + required=false 降级模式
- **复用订单状态机**：OrderStatusServiceImpl.transition() 已支持 REFUND 操作和 AFTER_SALE→CANCELLED 路由
- **管理端前端复用现有 RuoYi 框架**：Element Plus + Vue 3 组件库
- **退款方式仅微信支付原路返回**：不接入支付宝或其他渠道
- **US1 仅涉及管理端 + API 层**：管理端发起退款操作，退款数据结构提供 C 端查询字段；小程序端（含退款进度展示和 US2/US3 用户操作界面）需另行开发，当前 scope 不包含
- **已有订单管理页面作为退款入口**：退款操作在订单详情页增加"退款"按钮
- **补偿定时任务复用现有模式**：参考 PaymentCompensationTask 的 Redisson 分布式锁 + 固定间隔扫描
- **配送员与商家一致**：order_info 已有配送员字段（delivery_by/delivery_name/delivery_phone），但不拆独立模块；配送员独立接单后续再说
