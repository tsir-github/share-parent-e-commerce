## User Scenarios & Testing

### User Story 1 — 首次登录自动注册 + 补全昵称头像 (Priority: P1) 🎯 MVP

用户第一次打开小程序，点击"微信授权登录"，系统自动创建账号。登录后弹窗引导用户授权微信头像和昵称，点击允许后头像和昵称更新到个人信息中。

**Why this priority**: 当前首次登录的昵称是毫秒时间戳、头像为空，用户体验极差。这是最基础的用户身份建设。

**Independent Test**: 删掉测试用户数据，用微信扫码打开小程序，点登录后自动进入主页，弹窗提示"完善个人信息"，点击允许后头像和昵称正常显示。

**Acceptance Scenarios**:

1. **Given** 用户从未使用过该小程序，**When** 用户点击"微信登录"，**Then** 系统自动创建账号并返回登录态，页面显示引导完善信息的入口
2. **Given** 新用户登录后弹窗引导完善信息，**When** 用户点击允许授权，**Then** 微信头像和昵称更新到用户信息中，页面刷新展示新头像昵称
3. **Given** 新用户登录后弹窗引导完善信息，**When** 用户点击拒绝授权，**Then** 仍可正常使用，但头像昵称保持默认占位状态

---

### User Story 2 — 老用户静默登录 (Priority: P1)

老用户再次打开小程序，无需任何操作，自动完成登录，直接进入首页。

**Why this priority**: 登录不应成为高频操作的阻碍。老用户应该无感登录。

**Independent Test**: 已注册用户杀掉小程序进程重新打开，3秒内自动进入首页，无任何弹窗或登录按钮。

**Acceptance Scenarios**:

1. **Given** 用户之前已登录过且授权未过期，**When** 用户再次打开小程序，**Then** 无需任何操作自动进入首页
2. **Given** 用户登录态已过期，**When** 用户打开小程序，**Then** 自动调用 wx.login 重新获取 code 并刷新登录态（无需用户点击）

---

### User Story 3 — 已登录用户更换头像昵称 (Priority: P2)

已登录用户进入个人中心，可手动更换头像和昵称。头像从相册选择或拍照，昵称通过输入框修改。

**Why this priority**: 用户偶尔想换头像/昵称。已有头像上传接口（前面刚做的），只需补充昵称修改。

**Independent Test**: 已登录用户进入个人中心，点击头像更改并拍照上传，修改昵称并保存，刷新后新头像和昵称生效。

**Acceptance Scenarios**:

1. **Given** 已登录用户在个人中心，**When** 点击头像选择新图片并确认，**Then** 头像更新成功
2. **Given** 已登录用户在个人中心，**When** 修改昵称并保存，**Then** 昵称更新成功
3. **Given** 用户输入的昵称超过长度限制，**When** 系统校验，**Then** 提示"昵称不能超过20个字"

---

### User Story 4 — 绑定手机号（可选）(Priority: P3)

用户可在个人中心通过微信手机号快速授权绑定手机号。后端解密微信返回的加密数据获取手机号并保存。

**Why this priority**: 手机号是后续做收货地址默认填充、订单通知的基础。但不是登录的必要条件，设为可选。

**Independent Test**: 用户进入个人中心点击"绑定手机号"，通过微信授权获取手机号并保存。

**Acceptance Scenarios**:

1. **Given** 用户未绑定手机号，**When** 点击"绑定手机号"并微信授权，**Then** 手机号更新到个人信息中

### Edge Cases

- 用户拒绝微信头像昵称授权后，仍可正常使用，后续可在个人中心手动设置
- 同一个微信 openid 重复登录，不创建重复账号
- 小程序登录态过期后，前端调用 wx.login 重新获取 code，后端自动刷新 JWT token
- 昵称含特殊字符或 emoji，允许保存（微信昵称本身就支持 emoji）

## Requirements

### Functional Requirements

- **FR-001**: 系统必须支持首次微信授权登录时自动创建用户账号（openid 为唯一标识）
- **FR-002**: 新用户首次登录后，系统必须返回标识让前端判断是否为新用户，以便弹窗引导授权头像昵称
- **FR-003**: 系统必须提供更新用户头像和昵称的接口（头像上传复用已有上传能力）
- **FR-004**: 老用户已登录态未过期时，系统必须支持静默登录（无需用户点击）
- **FR-005**: 系统必须在 wxLogin 返回结果中包含 JWT token、用户基本信息、是否新用户的标识
- **FR-006**: 昵称长度限制 1-30 个字符，支持中文、英文、数字、emoji
- **FR-007**: 系统必须提供获取当前用户信息的接口

### Key Entities

- **UserInfo**: 已有实体。本次涉及字段：`nickname`（从时间戳改为真实昵称）、`avatar_url`（从空字符串改为微信头像或上传头像）、`phone`（可选绑定手机号）

## Success Criteria

- **SC-001**: 新用户从打开小程序到完成登录+授权头像昵称，全程不超过 15 秒
- **SC-002**: 老用户打开小程序到进入首页，不超过 3 秒（静默登录）
- **SC-003**: 99.9% 的登录请求成功创建或返回用户（排除微信 API 不可用的极端情况）

## Assumptions

- 微信小程序已配置 appId 和 secret（Nacos 中已有配置）
- 用户主动触发头像昵称授权（微信已废弃静默获取能力，必须用户点击按钮授权）
- 小程序前端会配合实现 wx.login → 调后端 → 判断 isNewUser → 弹窗引导授权 → 调更新接口
- 头像上传能力已在之前的功能中完成，本功能可直接复用
- 手机号绑定功能依赖微信小程序基础库 2.21.2+ 的 `getPhoneNumber` 能力
