# Feature Specification: 秒杀活动管理后台

**Feature Branch**: `014-flash-sale-admin`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: "秒杀管理后台 开发这个接口，自己判断属于哪个角色、缺不缺表/字段。请贴合此项目并摸清此接口痛点，最后解决。"

## User Scenarios & Testing

### User Story 1 — 管理员创建秒杀活动 (Priority: P1)

平台管理员选择一件商品并指定其 SKU，设置秒杀价、秒杀库存、每人限购数量、活动起止时间，创建一个新的秒杀活动。

**Why this priority**: 创建活动是所有后续操作（编辑、上下架、统计）的基础，没有活动则其他功能无从谈起。

**Independent Test**: 管理员登录后在秒杀活动列表页点击"新增"，填写商品/SKU/秒杀价/库存/时间等信息提交，列表页出现新活动记录。

**Acceptance Scenarios**:

1. **Given** 管理员已登录且有秒杀活动管理权限，**When** 填写活动信息（商品、SKU、秒杀价、库存、限购数、起止时间）并提交，**Then** 系统创建活动成功，列表中出现该活动
2. **Given** 管理员填写活动时选择了一个已下架的商品，**When** 提交表单，**Then** 系统提示"所选商品已下架，请重新选择"
3. **Given** 管理员设置的秒杀价不低于或等于 0，**When** 提交表单，**Then** 系统提示"秒杀价必须大于 0"
4. **Given** 管理员设置的活动结束时间早于开始时间，**When** 提交表单，**Then** 系统提示"结束时间不能早于开始时间"
5. **Given** 管理员设置的秒杀库存大于商品 SKU 的现有库存，**When** 提交表单，**Then** 系统给出警告提示但允许继续创建

---

### User Story 2 — 管理员查看和管理秒杀活动列表 (Priority: P1)

管理员可以分页查看所有秒杀活动，按活动名称/状态/时间范围筛选，看到每个活动的商品信息、秒杀价、库存、参与人数等关键数据。

**Why this priority**: 列表页是管理后台的核心入口，管理员需要快速了解所有活动的运行状况。

**Independent Test**: 打开秒杀活动管理页面，看到活动列表表格，支持按名称搜索和状态筛选。

**Acceptance Scenarios**:

1. **Given** 系统中有多个秒杀活动，**When** 管理员打开活动列表页，**Then** 系统以分页形式展示活动列表，每页显示活动名称、关联商品、秒杀价、库存、已售数量、起止时间、状态
2. **Given** 活动列表中有不同状态的活动（未开始/进行中/已结束/已禁用），**When** 页面加载，**Then** 每个活动的状态用不同颜色标签清晰标示
3. **Given** 管理员在搜索框输入部分活动名称，**When** 点击搜索或按回车，**Then** 列表仅显示名称匹配的活动
4. **Given** 管理员选择状态筛选项（全部/未开始/进行中/已结束/已禁用），**When** 筛选条件变更，**Then** 列表更新为对应状态的活动
5. **Given** 时间筛选器选择起止日期范围，**When** 应用筛选，**Then** 仅显示在该时间范围内有重叠的活动

---

### User Story 3 — 管理员编辑和删除秒杀活动 (Priority: P2)

管理员可以对已创建但未开始的秒杀活动进行编辑修改，或删除不再需要的活动。

**Why this priority**: 活动在创建后可能因价格调整或库存变化需要修改，保证运营的灵活性。

**Independent Test**: 点击活动行的"编辑"按钮，修改秒杀价并保存，确认变更已生效。

**Acceptance Scenarios**:

1. **Given** 一个状态为"未开始"的秒杀活动，**When** 管理员编辑其秒杀价或库存，**Then** 修改成功保存，列表页显示更新后的值
2. **Given** 一个状态为"进行中"的秒杀活动，**When** 管理员尝试编辑秒杀价，**Then** 系统提示"活动进行中，无法修改价格，请先禁用活动"
3. **Given** 一个状态为"进行中"的秒杀活动，**When** 管理员尝试增加库存，**Then** 允许修改（仅支持加库存，不支持减库存）
4. **Given** 一个秒杀活动已有用户参与记录，**When** 管理员尝试删除，**Then** 系统提示"该活动已有参与记录，无法删除"并拒绝操作
5. **Given** 一个秒杀活动没有任何参与记录，**When** 管理员点击删除，**Then** 活动被逻辑删除

---

### User Story 4 — 管理员启用/禁用秒杀活动 (Priority: P1)

管理员可以手动控制秒杀活动的上下架状态：启用后活动对 C 端用户可见可参与，禁用后立即停止。

**Why this priority**: 运营过程中可能出现商品库存不足、价格错误等突发情况，需要立即停止活动。

**Independent Test**: 将一个"未开始"的活动手动"启用"，确认状态变为"进行中"；再将其"禁用"，确认 C 端不再展示。

**Acceptance Scenarios**:

1. **Given** 一个状态为"未开始"的秒杀活动且已到活动开始时间，**When** 管理员点击"启用"，**Then** 活动状态变为"进行中"，C 端用户可见可参与
2. **Given** 一个状态为"进行中"的秒杀活动，**When** 管理员点击"禁用"，**Then** 活动状态变为"已禁用"，C 端立即下架
3. **Given** 一个状态为"已禁用"的秒杀活动，**When** 管理员点击"启用"且当前时间在活动时间范围内，**Then** 活动状态恢复为"进行中"
4. **Given** 一个已结束的活动（end_time 已过），**When** 管理员点击"启用"，**Then** 系统提示"活动已结束，无法启用"

---

### User Story 5 — 管理员查看秒杀活动统计 (Priority: P3)

管理员可以看到每个秒杀活动的参与数据：总浏览人数、抢购人数、下单人数、支付人数、支付率等关键指标。

**Why this priority**: 数据驱动运营决策，管理员需要了解活动效果来优化后续活动策略。

**Independent Test**: 在活动详情页看到统计面板，显示参与人数、订单数、支付数等指标。

**Acceptance Scenarios**:

1. **Given** 一个秒杀活动有用户参与，**When** 管理员在活动详情页查看统计，**Then** 页面展示：活动浏览数、抢购点击数、成功下单数、已支付数、支付转化率
2. **Given** 一个秒杀活动刚创建还未开始，**When** 查看统计数据，**Then** 所有指标显示为 0

---

### Edge Cases

- 秒杀活动开始瞬间大量并发请求，秒杀库存扣减需保证原子性不超卖
- 秒杀活动进行中，关联的商品被管理员下架或删除——活动应自动失效或提示冲突
- 多个秒杀活动时间范围重叠且使用同一 SKU——同一 SKU 同一时间只能属于一个进行中的秒杀活动
- 用户已下单但未支付，秒杀库存已被占用——订单超时未支付后需自动回滚库存（RocketMQ 延迟消息）
- 活动结束时仍有未支付订单——活动结束后未支付订单自动取消并释放库存
- 秒杀价不得高于商品原价——平台风控规则（可配置）

## Requirements

### Functional Requirements

- **FR-001**: 管理员必须登录且拥有 `goods:seckill:list` 权限后才能访问秒杀活动管理页面
- **FR-002**: 系统必须支持创建秒杀活动，填写活动名称、关联商品/SKU、秒杀价、秒杀库存、每人限购数量、活动起止时间
- **FR-003**: 系统必须支持分页查询秒杀活动列表，按活动名称模糊搜索，按状态（全部/未开始/进行中/已结束/已禁用）和时间范围筛选
- **FR-004**: 系统必须支持查看单个秒杀活动的完整详情
- **FR-005**: 系统必须支持编辑未开始的秒杀活动（活动进行中仅允许增加库存，不允许修改价格和其他关键参数）
- **FR-006**: 系统必须支持逻辑删除未开始且无参与记录的秒杀活动
- **FR-007**: 系统必须支持手动启用/禁用秒杀活动，禁用后 C 端立即不可见
- **FR-008**: 系统必须支持查看秒杀活动的统计数据（浏览数、抢购数、下单数、支付数、支付率）
- **FR-009**: 系统必须进行参数校验：秒杀价 > 0、结束时间 > 开始时间、库存 >= 0、限购数 >= 0
- **FR-010**: 同一 SKU 在同一时间范围内只能属于一个进行中的秒杀活动（时间冲突检测）
- **FR-011**: 系统必须记录操作日志（新增/修改/删除/启用/禁用），遵循项目 `@Log` 注解模式
- **FR-012**: 活动结束后自动变为已结束状态（基于系统时间与 end_time 对比）

### Key Entities

- **SeckillActivity（秒杀活动）**: 核心实体，记录活动名称、关联商品/SKU、秒杀价、秒杀库存、每人限购数量、活动起止时间、状态。一个活动针对一个 SKU，一个 SKU 在一个时间窗口内只能参与一个活动。
- **SeckillRecord（秒杀记录）**: 用户参与记录，记录用户ID、活动ID、订单号、抢购时间、状态（已抢购/已支付/已取消）。用于幂等校验和限购判断。
- **Product（商品）**: 秒杀活动关联的 SPU，提供商品名称、主图等信息（已有实体）
- **ProductSku（商品 SKU）**: 秒杀活动关联的 SKU，提供原价、库存等信息（已有实体）
- **OrderInfo（订单）**: 秒杀生成的订单，通过 `order_type=1` 标记为秒杀订单（已有实体）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 管理员可以在 2 分钟内完成一个秒杀活动的创建和发布
- **SC-002**: 活动列表页加载时间不超过 3 秒（100 条活动数据以内）
- **SC-003**: 活动进行中时，管理员禁用操作后 5 秒内 C 端不再展示该活动
- **SC-004**: 管理员可以清晰看到每个活动的参与数据，包括抢购、下单、支付的完整转化漏斗
- **SC-005**: 新增/编辑/删除/启用/禁用操作均正确记录操作日志，追溯周期不低于 90 天

## Assumptions

- 秒杀功能归属于 **share-goods** 模块（`seckill_activity` 表已在该模块数据库，商品/SKU 实体也在此模块）
- 角色为 **平台管理员**，使用 `@RequiresPermissions` 鉴权，Controller 继承 `BaseController`，使用 `AjaxResult`/`TableDataInfo` 返回类型
- 已有 `seckill_activity` 表但需改造补充字段（`limit_per_user`、`merchant_id`、`version`、审计字段、索引）
- C 端秒杀抢购逻辑（前端页面、下单接口、库存扣减等）不在本次范围内，仅开发管理后台
- 秒杀活动的状态由 `status` 字段 + 系统时间共同决定（`status=1 且 start_time <= now <= end_time` 为进行中）
- 已有 `product_sku.version` 乐观锁可复用于秒杀库存扣减
- 已有 RocketMQ 延迟消息机制可复用于秒杀订单超时处理
